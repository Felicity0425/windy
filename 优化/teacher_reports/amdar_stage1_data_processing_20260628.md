## 2. 结论摘要

1. `amdar.xlsx` 确实存在大量“同一航班、同一时间戳、但空间上分散成很多点”的情况，而且这不是零星异常，而是主体现象。
2. `location` 清洗主链路目前是正确的；主要剩余问题是少量缺失地速和极少数超高地速记录，不改变其可作为轨迹/运动约束来源的结论。
3. `turb` 清洗主链路目前也是正确的；其结构明显比 AMDAR 干净得多，没有大规模同时间多点展开问题。
4. 当前 AMDAR 的核心风险不是高度单位，而是时间字段语义。原始表头只有 `时间（北京时）`，没有更细的逐点观测秒、时延、子报文序号等字段。
5. 基于原始表结构，现阶段不能把“同航班同时间重复 AMDAR”继续当作严格单点真值；更保守的处理是全部降级为 `support_only_not_strict_truth`，只作为 support-only 融合输入。
6. `风速` 单位本次不建议直接改。虽然数值分布很像航空风速常见口径，但在 AMDAR 时间语义尚未厘清前，直接整体做 `kt -> m/s` 重标定证据仍不足。

## 3. 原始表头核查

### 3.1 AMDAR 原始表头

`amdar.xlsx` 只有一个工作表，首行字段为：

```text
机尾号, 航班号, 时间（北京时）, 飞行阶段, 纬度, 经度, 高度, 静温, 风向, 风速
```

样例前两行：

```text
B-5688, MF8054, 2026-01-23 00:00:39, DES, +28.421667, +113.41333, 5930, -00.2, 043, 004
B-5688, MF8054, 2026-01-23 00:00:39, DES, +28.435000, +113.35667, 4900, -02.2, 048, 002
```

### 3.2 直接含义

- 原始 AMDAR Excel 并不包含额外的逐点时间字段。
- 因此 `时间（北京时）` 很可能是批次时间、接收时间或报文统一时间标签，而不是每一个点的真实测量秒。
- 这与 AMDAR 业务背景是一致的：一个批次导出后，可能出现多个点共享同一个分钟级/秒级标签。

## 5. 对 AMDAR 时间字段的判断

### 5.1 当前最稳妥判断

`时间（北京时）` 不能再默认解释为“每一行观测点的真实测量时刻”。

更合理的解释是：

- 它可能是报文接收时间；
- 可能是批处理时间；
- 也可能是一个合并后的统一时间标签。

### 5.2 为什么不能继续按单点真值使用

如果继续把这些记录当作“严格单点真值”，会出现：

1. 同一 `flight_id + time_utc` 下有多个空间上相距很远的点；
2. 与 `location` 做最近时间对齐时，中位水平错位仍很大；
3. 这会把 Stage4 strict holdout 的时空匹配基础破坏掉。

## 9. 处理策略修正

### 9.1 已做修正

已修改 `stage/stage1_prepare.py`：

- 为 wind 数据保留 `source_row_index`
- 为同时间组保留：
  - `same_time_group_source_row_span`
  - `same_time_group_row_index_min`
  - `same_time_group_row_index_max`
- 对 AMDAR 采用新的保守策略：
  - 只要 `source=amdar` 且 `same_time_group_rows > 1`
  - 一律标记为 `support_only_not_strict_truth`
  - 排除原因统一记为 `amdar_same_timestamp_duplicate_batch`

### 9.2 新策略的原因

此前仅把 `hspan >= 0.5°` 的 AMDAR 组降级，还是偏宽松。

但从原始 Excel 结构和样本核查结果看：

- 即使水平跨度较小；
- 只要是同航班同时间重复；
- 本质上都缺少逐点真实观测秒；
- 因而都不适合作为 strict truth。

### 9.3 现阶段推荐口径

1. AMDAR 单时间重复组：
   - 作为 support-only 融合输入保留
   - 不进入 strict holdout truth candidate
2. AMDAR 单时间单点组：
   - 可继续保留为 `strict_truth_candidate`
3. `location`：
   - 继续作为轨迹/运动约束来源
4. `turb`：
   - 继续作为风观测补充来源

## 10. 关于“如何确切处理”

### 10.1 当前 Excel 条件下能做的最稳妥方案

由于原始 Excel 没有逐点时间秒，当前最稳妥方案是：

1. 不把同时间重复 AMDAR 当作 strict truth；
2. 保留原始行序信息；
3. 后续若要恢复轨迹，可在同一组内按：
   - 原始行序
   - 高度单调性
   - 经纬度沿航迹推进方向
   做轨迹重排研究。

### 10.2 你提出的三种方向，当前建议如下

1. 检查原始格式 / BUFR  
   - 这是最优解。  
   - 如果还能拿到 BUFR 或更原始报文，应优先解析逐点真实观测时间，而不是继续依赖 Excel 汇总表。

2. 在分钟尺度上聚合  
   - 在现有 Excel 条件下是可行备选。  
   - 但它更适合作为 support aggregation，不适合作为 strict single-point truth。

3. 根据实际轨迹排序  
   - 这条路有价值。  
   - 当前样例显示原始行序通常已经接近沿轨迹排序。  
   - 但在没有真实秒级时间之前，仍不建议把排序后的点直接当作严格真值。

### 10.3 基于 ADS-B / location 轨迹的重建时间方案

你提出的方案本身是合理的，且比“直接相信 AMDAR 原始时间”更稳妥：

1. 先按航班号筛选 ADS-B 候选轨迹；
2. 再按连续航段拆分；
3. 不把 AMDAR 原始时间当硬约束，只当宽松参考；
4. 按经纬度、高度和航向去找候选 ADS-B 轨迹位置；
5. 要求所有匹配点在 ADS-B 时间轴上单调递增；
6. 在相邻 ADS-B 点间插值，给出 AMDAR 点的估计 UTC 时间；
7. 保留原始时间、重建时间、匹配距离和时间不确定度。

我已经实现了一个工程原型脚本：

- `/data/LFT-W02_data/pengxu/stage/reconstruct_amdar_time_from_adsb.py`

当前原型做了以下事：

- 使用 `clean_loc.parquet` 作为 ADS-B/轨迹来源；
- 先按 `flight_id` 聚类；
- 对每个 `flight_id` 用大时间间隔切分连续航段；
- 对每个 AMDAR 同时间组做单调匹配；
- 输出：
  - AMDAR 原始时间
  - 重建时间
  - 匹配到的 ADS-B 点时刻/位置/高度
  - 水平距离
  - 垂直距离
  - 航向差
  - 时间不确定度

### 10.4 这条 ADS-B 重建方案的样本结果

对 `5000` 行 AMDAR 样本运行原型后，得到：

- AMDAR 行数：`5000`
- AMDAR 重复时间组数：`521`
- 匹配成功行数：`4935`
- 匹配成功组数：`515`
- 行级匹配覆盖率：`0.987`

但当前原型的几何质量还不够理想：

- 匹配水平距离中位数：`24.98 km`
- 匹配水平距离 90 分位：`46.58 km`
- 匹配垂直距离中位数：`164.59 m`
- 匹配垂直距离 90 分位：`1232.92 m`
- 航向差中位数：`62.76°`
- 航向差 90 分位：`157.85°`

这说明：

1. 这条路在工程上是可行的；
2. 仅靠当前启发式评分，覆盖率高，但匹配质量还不够强；
3. 现在更适合作为“重建时间研究分支”，还不适合直接写回 Stage1 主链。

### 10.5 为什么当前还不能直接并入 Stage1 默认链路

主要原因不是方法方向错，而是当前原型还不够严格：

1. `location` 的 `flight_id` 本身按航班号聚合，跨天复用很严重；
2. 必须先做更稳的连续航段切分；
3. 当前匹配评分只用了经纬度、高度、航向的简单加权；
4. 还没有充分利用：
   - 上升/下降阶段约束
   - 速度连续性
   - 更细的局部插值质量检查
   - 段内双向一致性约束

所以当前建议是：

- 先保留它作为独立研究脚本；
- 不直接覆盖 Stage1 默认 `time_utc`；
- 等匹配距离和航向差进一步压下来，再考虑纳入正式主链。

## 11. 风速单位结论

本次结论仍然是：**暂不修改 AMDAR/TURB 风速单位。**

原因：

1. 当前最致命的问题是时间语义，不是风速向量分解公式。
2. 现有文档没有给出原始字段单位说明。
3. 在时间字段未厘清时，贸然改单位会把另一个不确定性叠加进去。

## 12. 下一步建议

1. 如果能获取更原始的 AMDAR 报文，优先追溯 BUFR 或等价原始编码。
2. 若只能继续使用 Excel 汇总表，保持当前保守策略：
   - 重复同时间 AMDAR 全部 support-only
   - 不作为 strict holdout truth
3. 后续可单独开发一条“AMDAR 批次轨迹重排 / ADS-B 重建时间”研究分支：
   - 利用 `source_row_index`
   - 结合 `location`
   - 结合连续航段切分
   - 估计伪时间顺序
   - 但与 official strict truth 分支分开。

## 13. 最终结论

当前项目中，Stage1 的 `location` 和 `turb` 清洗链路基本正确；真正的问题集中在 AMDAR 时间字段的语义误判。`amdar.xlsx` 大量记录表现为“同航班同时间、但空间分散成多个点”，结合原始表头缺少逐点观测秒这一事实，最稳妥的工程处理是：所有同时间重复 AMDAR 一律不再作为严格真值，只保留为 support-only 融合输入。基于 ADS-B/location 的重建时间方案是值得继续推进的，但当前更适合作为独立研究分支，而不是立刻替换 Stage1 默认时间链路。
